# Typed build identity v2 foundation

`TypedBuildIdentityV2` defines bounded, versioned identity claims for future typed-build cache work. It is an additive API foundation only: it does not admit a cache, authenticate a cache manifest, prove cached and cold builds equivalent, or enable a cache path. Current reports and runtime manifests remain v1, and the existing cold provider behavior is unchanged.

Every digest uses `fed-canonical-json-v1`, an explicit domain tag, UTF-8 JSON with sorted mapping keys, and tagged value encodings that distinguish booleans, integers, floats, strings, bytes, lists, tuples, sets, frozensets, mappings, and null. Non-finite floats and unsupported values fail closed. Payloads are bounded to 1 MiB, 10,000 values, depth 16, and 64 KiB per scalar string/byte value. These are canonical identity inputs, not a general JSON canonicalization standard.

The semantic projection is pinned to Mypy 1.19.1. It excludes exactly `incremental`, `cache_dir`, and `cache_map`; all three remain in the complete inspectable actual-options record and affect actual build/provenance digests. Unknown option fields, option value types, or Mypy versions fail closed. The caller-supplied semantic context must include canonical root and import/search paths, resolved module fullname/path/origin/side identities, source inventory facts, analyzer settings, plugin identity, and relevant toolchain identity. The actual build context additionally captures engine/runtime/config/invocation facts. These digests bind supplied facts; they do not authenticate those facts.

The object keeps the full bounded canonical actual-options and provenance records alongside their digests, allowing inspection rather than asking reviewers to trust a digest alone. `cache_attestation_sha256` is null for `cold` and `cold_fallback`; a fallback carries a bounded reason and cannot claim a hit. An `authenticated_dependency_hit` disposition requires a non-null attestation digest, no fallback reason, and a complete caller-supplied fact set (manifest digest, trust label, observed hit, fresh project modules, selected consumers, and source recheck status). These supplied fields are declarations only: the object does not verify the attestation, independent trust, freshness, or equivalence. A digest or trust label is not authentication. Do not construct that disposition from a cache run without a separate authenticated admission protocol.

Future cache integration remains a separate change. It must version the phase report and runtime manifest together, preserve all v1 bytes and meanings on default cold calls, put semantic and provenance identity classes on every record/manifest entry, reject mixed or unknown schemas, and prove authenticated custody, full source/toolchain/resolution identity, selected-consumer freshness, and complete cold/cache output and diagnostic parity before returning cached results. Until those gates and trusted unchanged-cap VM canaries pass, the supported behavior remains cold and cache use remains unavailable.
